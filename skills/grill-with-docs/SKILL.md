# grill-with-docs

通过高强度的反问与探索性验证，把用户脑中模糊、隐式的设想逐层剥离并清晰化。将领域术语沉淀为全局一致的词汇表，将难以逆转的重大技术抉择写成正式的架构决策记录（ADR）。

## 核心原则

1. **每个问题必须有解**：提出的每个问题，必须**要么在对话中由人类/需求方直接回答**，**要么通过一次可运行的代码/测试/命令验证得出确定性结论**。杜绝泛泛而谈的悬空问题。
2. **术语先于设计**：未统一定义的词汇必然导致沟通变形，所有新概念必须立即入库词汇表。
3. **单向门决策必须有据**：难以逆转的抉择（单向门，One-Way Door）绝不能口头带过，必须落地为结构化 ADR。

## 执行步骤

### 1. 概念捕获与歧义扫描
- 倾听用户输入的原始描述，识别出包含多义性、口语化或假设性的关键词（例如：“快速缓存”、“轻量级”、“实时同步”）。
- 在 `GLOSSARY.md` 中建立/更新概念定义：
  - **名词/术语**：中英文对照与确切范围。
  - **清晰边界**：该术语**包含什么**，**明确不包含什么**。
  - **关联代码实体**：对应到系统中的具体模块、类或表结构。

### 2. 深度追问循环 (The Grilling Loop)
针对关键链路展开极限场景提问，直到模糊地带消除：
- **边界与极限**：容量上线、并发峰值、网络分区或超时怎么表现？
- **失败与退化**：依赖服务挂掉时是快速失败还是静默降级？
- **一致性与生命周期**：数据何时创建、何时清理、谁负责补偿？
- **验证方式抉择**：
  - 若属于**业务取舍/偏好**：组织成带明确选项与后果的多选提问，让用户在对话中直接定夺。
  - 若属于**技术假设/可行性疑点**：编写最小验证脚本（PoC）或运行已有命令获取证据，以客观事实回答。

### 3. 单向门判断与 ADR 沉淀
当面临以下难以逆转的决策（单向门）时，必须撰写 ADR：
- 引入新的重度第三方基础设施、框架或协议。
- 数据库表核心主键设计、分库分表键或跨系统数据不可变契约。
- 核心通信模型（如事件溯源 vs 状态快照，同步 RPC vs 异步 MQ）。

**ADR 标准结构**：
```markdown
# ADR-001: [简短决策标题]

## 状态 (Status)
[提议 / 已采纳 / 已废弃 / 被替代]

## 背景与问题陈述 (Context)
面临什么具体约束与技术瓶颈？为什么不能沿用现有方案？

## 单向门评估 (One-Way Door Analysis)
逆转该决定的成本是什么？一旦采纳，撤回需要付出多少时间与兼容性代价？

## 备选方案评估 (Alternatives Considered)
- 方案 A（当前选择）：优势与缺陷。
- 方案 B（备选）：未选择的根本原因。

## 最终决策 (Decision)
我们决定采用...，理由是...。

## 后果与权衡 (Consequences)
- 积极影响：带来了什么能力提升。
- 负面影响 / 妥协：引入了什么额外复杂度，如何监控缓解。
```
