# to-spec

把长篇累牍、发散讨论的用户对话与研讨内容收敛为一份结构严密、无二义性的规格文档（Specification）。**丢弃所有推演过程、闲聊与临时猜测，仅保留确定性的系统行为契约与验收标准**，使后续每一步（拆票、开发、测试、审查）都能直接引用本 Spec 进行对照。

## 核心原则

1. **零过程噪音**：讨论中的“我本来想用方案 A”、“刚才算错了”等推演过程一律丢弃；仅在“非目标（Out of Scope）”中记录明确否决的路线。
2. **唯一真实源 (Single Source of Truth)**：后续工单、测试用例和代码实现均严格锚定此 Spec，不在 Spec 之外私自衍生隐藏行为。
3. **机器与人类双重可读**：契约、数据结构与接口声明必须精确无歧义，能直接指导代码与单测编写。

## Spec 标准结构规范

```markdown
# [功能名称] 规格说明书 (Specification)

## 1. 目标与价值 (Goals)
- 一句话说明该功能解决的核心问题与最终交付状态。

## 2. 范围边界 (Scope Boundaries)
### 2.1 明确包含 (In Scope)
- 必须交付的能力 1
- 必须交付的能力 2
### 2.2 明确排除 (Out of Scope / Non-Goals)
- 本阶段坚决不做的特性、不兼容的旧场景或已否决的妥协方案。

## 3. 核心契约与数据模型 (Contracts & Data Models)
- **输入/输出接口**：严格的字段名称、类型、必填性、默认值及校验规则。
- **状态流转图**：生命周期状态、合法跃迁条件、非法跃迁行为。
- **错误与异常码**：标准错误代码、触发场景及客户端可见表现。

## 4. 行为与流程规范 (Behavior & Workflows)
- 正常主链路的时序或步骤描述。
- 边缘情况处理：超时、空值、幂等防重、并发竞争。

## 5. 验收标准 (Acceptance Criteria)
- [ ] AC-1: 当输入 ... 时，系统必须返回 ...，且状态变更为 ...
- [ ] AC-2: 当出现 ... 异常时，系统必须在 ... 毫秒内熔断并记录错误日志
```

## 信息收敛与过滤操作指南

执行转换时，按以下过滤规则清洗输入：

1. **剔除反问与试探**：丢弃所有“是不是这样”、“或者那样也可以”的摇摆语句，仅保留最终确认的行为分支。
2. **代码片段提纯**：对话中随意贴出的草稿代码，转化为规范的 TypeScript/JSON Schema/伪代码契约，补齐字段注释。
3. **锚定外部依赖**：将对话中提到的“用某个库”细化为明确的库名称、版本约束与依赖职责。
4. **统一命名与术语**：严格使用 `GLOSSARY.md` 中的标准词汇，消除别名与黑话。

## 验收与自检标准

- [ ] 文档中不含任何对话记录、发言人名称或“用户说/助手说”等推导痕迹。
- [ ] 所有业务边界均已明确为 In Scope 或 Out of Scope。
- [ ] 数据结构与接口签名完整，无类似“等等”、“其他参数看情况”的模糊占位。
- [ ] 验收标准均具备明确的断言条件（输入 -> 预期输出/副作用），支持后续无歧义拆票。
