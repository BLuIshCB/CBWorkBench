# CBWorkBench 开发边界与追踪分支规范

本文档明确定义 CBWorkBench 项目的代码版本追踪分支策略、系统开发职责边界、角色权限边界以及安全门禁规范。

---

## 1. 追踪分支策略 (Single Branch Strategy)

### 1.1 唯一主干原则
* **单一分支管理**：本仓库**严格遵循单分支策略**，不切分额外的开发分支、特性分支（feature branch）或发布分支（release branch）。
* **当前与唯一追踪分支**：
  * 本地活跃分支：`main`
  * 远端追踪分支：`origin/main` (`git@github.com:BLuIshCB/CBWorkBench.git`)
* **开发与提交规范**：
  * 所有功能开发、BUG 修复、文档更新均直接基于 `main` 推进。
  * 每次提交前必须保证完整离线测试套件全部通过（`npm test`）。
  * 严禁在日常开发中创建派生分支造成分支碎片化。

### 1.2 目标受管项目的工作区 Git 边界
* CBWorkBench 本身是一个任务推进工作台，被推进的项目称为「目标工作区（`target_cwd`）」。
* **工作台对目标项目的 Git 操作边界**：
  * 工作台**仅读取**目标项目的 Git 分支名称、工作区状态（`git status`）以及当前变更差异（`git diff`）。
  * **严禁工作台自作主张在目标项目中切换分支、执行 `git commit`、`git merge` 或 `git push`**。
  * 业务代码提交、分支合并与发布归档由人类工程师手动执行。工作台的任务完成状态与目标项目的发布审批各自独立。

## 2. 系统定位与职责边界 (Scope Boundaries)

```
┌─────────────────────────────────────────────────────────────┐
│                       主 Agent (cb-flow)                     │
│  职责：需求理解、业务沟通、架构规划、生成任务包 (不可直改代码)      │
└──────────────────────────────┬──────────────────────────────┘
                               │ MCP 提交 (须用户在对话中授权)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                    CBWorkBench 开发工作台                     │
│  职责：门禁守护、流程推进、串行调度、执行证据核验、日志追踪        │
│                                                             │
│  [对话授权]  ->  [Web 手动启动]  ->  [按模板执行与结项]       │
└──────────────┬───────────────────────────────┬──────────────┘
               │                               │
               ▼                               ▼
┌──────────────────────────────┐ ┌────────────────────────────┐
│      Worker 编码执行者       │ │     Verifier 验收审查者     │
│   (任意已注册 CLI / 开发提示词) │ │  (任意已注册 CLI / 验收提示词) │
│ 约定：按开发提示词修改目标目录 │ │ 约定：按验收提示词只读检查 │
└──────────────────────────────┘ └────────────────────────────┘
```

### 2.1 工作台「做的事」 (In Scope)
1. **统一任务包接收与冻结**：接收主 Agent 通过 MCP 工具提交的结构化任务包（包含开发清单、测试用例、验收标准、Worker 独立提示词等），并以版本号（`r1`, `r2`...）进行物理物理目录冻结。
2. **人工确认规则**
   - 门禁 1：对话内上传授权（无授权不上传）。
   - 门禁 2：Web 端手动启动确认（无点击不执行，MCP 严禁提供自启动工具）。
   - 人工审核由工作流模板配置。系统内置默认模板包含末尾人工复核。自定义模板可配置零个或多个人工节点，流程满足模板条件并到达结束节点后结项。
3. **串行调度与状态机推进**：按工作流调用各 Agent 执行开发/修复、测试验证和只读验收。测试节点自行选择并运行命令，工作台校验其提交的执行证据，不要求用户配置命令。
4. **过程凭据与日志留存**：记录每轮的提示词输入、大模型响应输出、测试进程退出码与 stderr/stdout，提供给前端与人工核验。
5. **已配置 CLI 适配器管理与探测**：在「🧩 适配器中心」实时查看三家 CLI 适配器启动状态，支持发送 Prompt 实时调试。

### 2.2 工作台「不做的事」 (Out of Scope / Non-Goals)
1. **不参与前期需求分析与发散讨论**：工作台不替代主 Agent，不与用户在工作台内进行开放式需求研讨。
2. **不擅自篡改既定契约**：工作台只能忠实执行已确认任务包中的标准，不能在循环过程中擅自放宽验收标准或跳过测试。
3. **不提供绕过门禁的后门**：任何 API、MCP 工具或脚本均不得提供跳过门禁 2 或门禁 3 的接口。
4. **不承载多租户/远程任务编排**：第一版坚持单机、单用户、单任务串行执行，不做分布式集群或复杂权限系统。

## 3. CLI 对话边界

WorkBuddy、Codex、Antigravity 共用 IAgentAdapter.execute()，通过独立 CLI 子进程执行。自动节点通过工作台提供的完成命令调用 MCP，工作台核验回执和进程退出状态，再按连线推进。

按当前要求不设置沙箱，使用各 CLI 的跳过交互审批参数。目标目录与只读验收要求由模型和提示词遵守，不形成操作系统权限隔离。验收证据由节点写入独立报告，工作台校验其内容与 MCP 结果一致。任务启动、节点测试与人工审核按工作流执行。

完整参数、登录隔离、会话持久化差异与验证命令见 [CLI 接入与验证](CLI接入与验证.md)。

## 4. 测试节点执行边界

1. **节点自行执行**：测试 Agent 根据项目与任务材料选择并真实运行命令，不修改业务代码；工作流不配置 `command` 字段。
2. **执行时限**：选择及运行命令包含在本次 Agent 节点的总时限内，超时或无法执行时如实报告阻塞。
3. **证据校验**：节点提交 `outputs/test_report.json`，包含实际命令、工作目录、退出码、stdout 和 stderr。工作台根据提交的退出码判定结果；证据缺失或无效时阻塞，非零退出码走失败路径，返工后须重新测试。证据来源是测试 Agent，不构成工作台另行独立执行测试的证明。
