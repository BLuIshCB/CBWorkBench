# CBWorkBench 开发边界与追踪分支规范

本文档明确定义 CBWorkBench 项目的代码版本追踪分支策略、系统开发职责边界、角色权限边界以及安全门禁规范。

---

## 1. 追踪分支策略 (Single Branch Strategy)

### 1.1 唯一主干原则
* **单一分支管理**：本仓库**严格遵循单分支策略**，不切分额外的开发分支、特性分支（feature branch）或发布分支（release branch）。
* **当前与唯一追踪分支**：
  * 本地活跃分支：`master`
  * 远端追踪分支：`origin/master` (`git@github.com:BLuIshCB/CBWorkBench.git`)
* **开发与提交规范**：
  * 所有功能开发、BUG 修复、文档更新均直接基于 `master` 推进。
  * 每次提交前必须保证完整测试套件（11 组单元/集成测试）全部通过（`npm test`）。
  * 严禁在日常开发中创建派生分支造成分支碎片化。

### 1.2 目标受管项目的工作区 Git 边界
* CBWorkBench 本身是一个任务推进工作台，被推进的项目称为「目标工作区（`target_cwd`）」。
* **工作台对目标项目的 Git 操作边界**：
  * 工作台**仅读取**目标项目的 Git 分支名称、工作区状态（`git status`）以及当前变更差异（`git diff`）。
  * **严禁工作台自作主张在目标项目中切换分支、执行 `git commit`、`git merge` 或 `git push`**。
  * 所有业务代码的提交、分支合并与发布归档，必须在第三道门禁（最终人工审核）通过后，由人类工程师手动执行。

## 2. 系统定位与职责边界 (Scope Boundaries)

```
┌─────────────────────────────────────────────────────────────┐
│                       主 Agent (cb-flow)                     │
│  职责：需求理解、业务沟通、架构规划、生成任务包 (不可直改代码)      │
└──────────────────────────────┬──────────────────────────────┘
                               │ MCP 提交 (须用户在对话中授权)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                    CBWorkBench 开发工作台                     │
│  职责：门禁守护、流程推进、串行调度、独立测试执行、日志追踪        │
│                                                             │
│  [门禁 1: 对话授权]  ->  [门禁 2: Web手动启动]  ->  [门禁 3: 人工审核]│
└──────────────┬───────────────────────────────┬──────────────┘
               │                               │
               ▼                               ▼
┌──────────────────────────────┐ ┌────────────────────────────┐
│      Worker 编码执行者       │ │     Verifier 验收审查者     │
│   (WorkBuddy CLI / deepseek) │ │  (Codex CLI / gpt-5.6-sol) │
│ 边界：仅在 target_cwd 内修代码 │ │ 边界：严格只读沙箱，不可写代码 │
└──────────────────────────────┘ └────────────────────────────┘
```

### 2.1 工作台「做的事」 (In Scope)
1. **统一任务包接收与冻结**：接收主 Agent 通过 MCP 工具提交的结构化任务包（包含开发清单、测试用例、验收标准、Worker 独立提示词等），并以版本号（`r1`, `r2`...）进行物理物理目录冻结。
2. **三道硬性物理门禁把关**：
   - 门禁 1：对话内上传授权（无授权不上传）。
   - 门禁 2：Web 端手动启动确认（无点击不执行，MCP 严禁提供自启动工具）。
   - 门禁 3：最终人工审核确认（无人类确认不结项）。
3. **串行调度与状态机推进**：按轮次调度 Worker 执行开发/修复、调用 TestRunner 独立运行测试命令、调用 Verifier 进行只读自动化验收。
4. **过程凭据与日志留存**：记录每轮的提示词输入、大模型响应输出、测试进程退出码与 stderr/stdout，提供给前端与人工核验。
5. **已配置 CLI 适配器管理与探测**：在「🧩 适配器中心」实时查看双 CLI 适配器运行状态，支持发送 Prompt 实时调试。

### 2.2 工作台「不做的事」 (Out of Scope / Non-Goals)
1. **不参与前期需求分析与发散讨论**：工作台不替代主 Agent，不与用户在工作台内进行开放式需求研讨。
2. **不擅自篡改既定契约**：工作台只能忠实执行已确认任务包中的标准，不能在循环过程中擅自放宽验收标准或跳过测试。
3. **不提供绕过门禁的后门**：任何 API、MCP 工具或脚本均不得提供跳过门禁 2 或门禁 3 的接口。
4. **不承载多租户/远程任务编排**：第一版坚持单机、单用户、单任务串行执行，不做分布式集群或复杂权限系统。

## 3. 适配器与执行者边界 (Worker & Verifier Boundaries)

当前系统基于 `IAgentAdapter` 契约体系，**严格仅保留双 CLI 适配器**：

### 3.1 Worker（WorkBuddy CLI）执行边界
* **适配器 ID**：`workbuddy`
* **底层协议**：Windows 具名管道（Named Pipe）/ Stdio MCP。
* **模型标准**：`deepseek-v4-flash`
* **权限边界**：
  * **限制在 `target_cwd` 目录内**：Worker 的读写操作必须局限在当前任务锁定的工作区路径下，严禁越界修改系统文件或全局环境变量。
  * **依赖既定输入**：Worker 必须依赖当前轮次派发的独立提示词、上一轮测试失败日志或验收退回意见开展修复，不保留跨任务的历史隐式状态。

### 3.2 Verifier（Codex CLI）验收边界
* **适配器 ID**：`codex`
* **底层协议**：命令行子进程只读沙箱 (`codex exec -s read-only`)。
* **模型标准**：`gpt-5.6-sol` (备选 `gpt-5-turbo`, `o3-mini`, `o1`)。
* **权限边界**：
  * **只读隔离**：Verifier 必须且只能在 `-s read-only` 模式下执行，**绝不具备任何文件写入、代码修改或外部工具执行权限**。
  * **结构化判定**：Verifier 仅根据代码快照、Working Tree Diff 和测试证据输出标准 JSON Schema 判定（`passed` / `needs_changes` / `blocked`），不得直接改写业务逻辑。

### 3.3 外部依赖与网络边界
* **拒绝无授权的第三方云端直连**：系统不开启未授权的 HTTP 代理或旁路 API 直连，统一通过配置明确的本地 CLI 管道与工具链通信。
* **保持代码精炼**：不引入未经论证的外部库，所有底层操作基于 Node.js 原生模块与轻量依赖。

---

## 4. 自动化测试执行边界 (Test Runner Boundaries)

1. **客观独立执行**：测试命令（如 `npm test`、`pytest` 等）由工作台本地子进程独立调用，**绝对不能依赖 Worker 口头声称的“测试已通过”**。
2. **超时与进程保护**：测试进程配置硬性超时熔断（默认 30s-60s），防止死循环、端口死锁或阻塞进程挂起工作台。
3. **真实证据捕获**：必须捕获进程退出码（Exit Code）、标准输出（stdout）及错误输出（stderr），作为 Codex 验收的必要物理凭据。
