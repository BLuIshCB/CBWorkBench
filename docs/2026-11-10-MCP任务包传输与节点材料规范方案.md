# MCP 任务包传输与节点材料规范方案

日期：2026-11-10。状态：已确认并完成实施（离线回归套件全部通过）。

本方案定义应用层协议 `cb.task-package/2.0`，通过 MCP 工具传输。结合项目 `GEMINI.md` 规范，确认如下设计基线：

1. **全面切换至统一节点材料协议，不保留旧协议兼容层**：直接删除旧版全局正文字段（`task_md`、`development_md`、`tests_md`、`acceptance_md`、`verifier_prompt_md`、`worker_prompts`）与旧提交/修订接口（`workbench_submit_task`、`workbench_revise_task`）。
2. **工作流模板不做版本号功能**：沿用工作流主键 `id` 就地修改与任务引用锁定保护，Manifest 与工作流查询通过 `workflow.id` + `definition_sha256` 校验并冻结工作流定义，不引入 `workflow_version`。
3. **仅支持本机路径导入（`local_path`）**：不实现文件分块/内容上传接口，主 Agent 在本机生成材料并传递本地包路径，工作台读取、校验并复制入实例数据目录留存副本。

本次取消上一版针对测试职责设计的特殊协议：工作台只管理普通任务节点、指令、资源、输入输出和执行记录。测试清单与其他文档一样，是节点拥有的普通资源。

## 1. 已核对的现状

- `src/server/mcpServer.ts` 已有工作流查询及节点提示词参数；任务正文仍是固定的全局开发、测试、验收字段。
- `src/config/constants.ts` 支持 `CB_DATA_DIR`，默认数据目录的推导涉及 `process.cwd()`，不能保证 EXE、快捷方式和 MCP 从不同位置启动时使用同一份数据。
- `src/entryExe.ts` 尚无本文拟议的 `--data-dir`、`--portable` 参数。
- 当前网页与 MCP 删除入口先删数据库记录，再调用文件删除；若后者失败，可能失去数据库中的任务入口。
- 执行服务存在进程引用、缓冲区和计时器；仅删文件不能替代运行时资源释放。

以上为本地源码分析，未确认运行中的 EXE 与源码一致。本次只修订文档，不修改实现或操作真实任务。

## 2. 统一节点模型

保留开始 `start`、结束 `end`、任务 `task` 三种控制类型。所有任务节点采用相同材料结构，不增加测试节点、验收节点等业务类型。

Agent、人工是执行机制，不是业务分类。命令由 Agent 节点根据任务自行选择并执行，工作流不配置命令。工作台不按节点名称、资源文件名或提示词关键词决定其业务能力。

| 工作台负责 | 主 Agent 和节点负责 |
| --- | --- |
| 节点 ID、连线、执行方式和状态 | 节点业务目标与具体工作步骤 |
| 文件归属、路径、大小、哈希与生命周期 | 开发清单、测试用例、验收清单等资源内容 |
| 按声明分发输入、登记输出和证据 | 按材料执行任务并解释业务结果 |
| 校验统一结果和通用输出契约 | 测试覆盖、业务标准等具体规则 |

例如“测试”和“编写说明”使用同样的目录，只是材料内容不同。开始、结束节点不执行工作，不生成空文档和提示词。

## 3. EXE 和源码共用稳定的数据目录

### 默认位置

Windows 默认使用当前用户的本地应用数据目录：

```text
%LOCALAPPDATA%/CBWorkBench/data/
```

通过系统位置或 `LOCALAPPDATA` 解析绝对路径，不硬编码用户名；无法解析时要求指定目录，不回退当前工作目录。

数据独立于 EXE、源码和业务项目。移动或升级 EXE、从快捷方式启动，继续读取同一目录。不把可变材料写进 EXE 内嵌资源，不默认写安装目录或系统临时目录。

### 可选配置

| 方式 | 规则 |
| --- | --- |
| `--data-dir <absolute_path>` | 显式指定目录，优先于环境变量；拟新增 |
| `CB_DATA_DIR` | 复用现有配置；新规范要求绝对路径 |
| `--portable` | EXE 显式便携模式，使用 `EXE所在目录/data`；拟新增 |
| 均未配置 | 使用当前用户本地应用数据目录 |

便携模式与显式目录配置同时出现时报冲突。便携目录不可写时明确失败，不静默切换，也不要求管理员权限。源码模式不采用 `--portable`。

EXE、源码和 MCP 复用同一解析规则；在初始化日志、数据库、文件存储前完成解析，不能等数据库模块打开后才解析参数。首次初始化生成持久 `instance_id`，MCP 能力查询返回实例 ID 和实际绝对数据目录。

MCP 与网页后台须使用同一实例。自定义目录或便携模式需要让 MCP 指定同一目录，或者连接对应的既有后台。目录或实例不符时明确报错，不能默默创建另一份任务库。同一数据目录只有一个常驻后台负责调度与文件生命周期，MCP 不成为第二个清理进程。

### 旧数据处理

默认位置调整必须作为数据迁移处理。发现旧 `data` 时保留原目录，提供目录选择或离线迁移流程；复制并核对数据库和资源后再切换。两个目录都有数据时不自动合并或覆盖。删除或升级 EXE 不自动删除用户数据。

## 4. 资源具体存放位置

```text
<DATA_DIR>/
  instance.json
  workbench.db
  workbench.log
  maintenance/
    deletions/                  未完成删除的恢复记录
  tasks/
    <task_id>/                  任务全部资源的归属根目录
      .staging/
        <draft_id>/             创建或修订中的上传草稿
      revisions/
        r0001/
          manifest.json
          shared/
            resources/         任务拥有的共同资源，可为空
          nodes/
            <node_id_a>/
              node.md
              prompt.md
              resources/
                <resource_files>
            <node_id_b>/
              node.md
              prompt.md
              resources/
                <resource_files>
      runs/
        r0001/
          <node_id_a>/
            <attempt_id>/
              context.json
              inputs/
              outputs/
              logs/
              temp/
```

每个任务节点固定为 `node.md + prompt.md + resources/`，资源可为空。运行目录另按修订、节点、尝试隔离，不把输出混入冻结材料。

节点目录名采用服务返回的安全编码。清单使用相对路径，迁移数据目录无需改写内部绝对地址。

数据库保存任务、修订、节点绑定、资源元数据和相对路径；正文及附件按文件存放、按需读取，不将全部历史材料常驻内存。第一版不做跨任务去重、全局附件池或跨任务硬链接。

共同资源也属于当前任务。两个任务导入同一个源文件时各存自己的副本；工作流模板不持有任务资源。

## 5. 相同的节点结构与资源声明

`node.md` 描述目标、输入、范围、工作项、完成条件、输出与阻塞处理。`prompt.md` 是节点指令：Agent 模式用于模型提示词，人工模式用于处理指引。测试验证 Agent 根据提示词和项目实际入口自行执行命令。

其他材料统一进入 `resources/`，例如：

```text
nodes/node-a/resources/implementation-checklist.md
nodes/node-b/resources/test-cases.md
nodes/node-c/resources/review-checklist.md
```

名称和内容由主 Agent 根据职责确定，工作台不为某个名称增加业务分支。允许的 Markdown、JSON、文本和附件都采用同一资源登记方式，上传文件本身不会触发执行。

统一节点描述示例：

```json
{
  "node_id": "node-b",
  "node_ref": "nodes/node-b/node.md",
  "prompt_ref": "nodes/node-b/prompt.md",
  "resources": [
    {
      "id": "resource-01",
      "path": "nodes/node-b/resources/test-cases.md",
      "description": "本节点需要执行的用例与预期结果"
    }
  ],
  "shared_refs": [],
  "input_bindings": [],
  "output_contract": {"required_outputs": ["result"]}
}
```

所有节点使用同一组字段，不增加 `test_cases_ref`、`test_plan_ref`、`verifier_prompt` 等专属字段。可选的 `output_contract.schema_ref` 引用本节点 JSON Schema 资源；服务只执行通用 Schema 校验，不根据文件名加载业务代码。

测试用例与证据要求写进该节点资源、指令和输出契约，后续节点按声明复核。测试验证节点由 Agent 自行运行命令并提交执行证据，工作流不配置 command。result_rule 为 verification 的节点提交 outputs/test_report.json（命令、工作目录、退出码、stdout、stderr）；工作台按提交的退出码判定，证据无效时阻塞。Agent 进程退出成功、资源齐全和结果结构合法，不直接等于业务测试通过。

## 6. 工作流发现与统一 Manifest

主 Agent 先查询真实工作流定义及其摘要（`definition_sha256`），读取任务节点的稳定 ID、职责、执行方式、默认指令、连线以及统一材料要求，再根据需求生成每个节点的材料。职责不明且影响正确性时标为阻塞，不靠名字猜测。

示例中的 `${...}` 必须替换为真实值；为简化展示仅列一个节点和一个文件登记项：

```json
{
  "protocol_version": "cb.task-package/2.0",
  "task_key": "example-task",
  "revision": 1,
  "title": "示例任务",
  "target_cwd": "D:/CODE/PROJECT",
  "workflow": {
    "id": "${workflow_id}",
    "definition_sha256": "${workflow_sha256}"
  },
  "readiness": "ready",
  "blockers": [],
  "nodes": [
    {
      "node_id": "node-b",
      "node_ref": "nodes/node-b/node.md",
      "prompt_ref": "nodes/node-b/prompt.md",
      "resources": [
        {"id": "resource-01", "path": "nodes/node-b/resources/test-cases.md"}
      ],
      "shared_refs": [],
      "input_bindings": [],
      "output_contract": {"required_outputs": ["result"]}
    }
  ],
  "files": [
    {
      "path": "nodes/node-b/resources/test-cases.md",
      "owner": {"scope": "node", "node_id": "node-b"},
      "media_type": "text/markdown",
      "size_bytes": 1234,
      "sha256": "${file_sha256}"
    }
  ]
}
```

完整包必须准确覆盖工作流所有任务节点，`files` 必须登记全部节点文档、提示词和资源。共同资源使用 `owner.scope=shared`。引用须对应已登记文件，不能引用其他节点的私有材料。

`target_cwd` 是业务工作目录，与工作台数据目录分开。任务包不能暗中修改工作流、执行器、模型、连线或次数限制。`ready` 只表示材料完整，不代表允许执行。

文本使用 UTF-8 无 BOM；大小、SHA-256 按原始字节计算，不自动转换换行。Manifest 不登记自身哈希，请求单独提供 `manifest_sha256`；文件全部核对后该值也作为包摘要。

## 7. 路径导入与长内容

区分上传源路径、包内相对路径和工作台资源引用。本方案仅支持同机路径导入（`source.mode = "local_path"`）：

```json
{
  "protocol_version": "cb.task-package/2.0",
  "operation": "create",
  "idempotency_key": "example-task:r1:${manifest_sha256}",
  "source": {
    "mode": "local_path",
    "package_root": "D:/CODE/PROJECT/.cb-flow/example-task/r01",
    "manifest_path": "manifest.json",
    "manifest_sha256": "${manifest_sha256}"
  }
}
```

服务读取、校验后复制进自身数据目录。正式任务不依赖上传源文件，也不会在删除任务时删除外部源目录。主 Agent 自己生成的临时材料如需清理，另行管理；服务不能沿上传路径删除用户文件。

包内路径禁止绝对路径、盘符、`..`、网络地址、大小写归一化后的重名，以及链接或 junction/reparse point 逃逸。只读取清单声明的普通文件，按实际字节核对哈希。

不实现跨机器文件分块/内容上传接口（`upload` 模式不受支持）。请求、文件及包的大小限制由能力查询返回；若源路径不可读或不存在，直接返回 `SOURCE_UNAVAILABLE` 明确报错，不能只存外部路径不校验拷贝就报告成功。

运行时先返回索引，资源按需分页读取；长文档可按语义拆分。路径引用缩小 MCP 请求，但不消除模型上下文限制。必需材料未读取完整时不得声称已完成检查。

## 8. MCP 工具和提交生命周期

| 工具 | 职责 |
| --- | --- |
| `workbench_get_package_protocol` | 返回 Schema、限制、支持的传输模式（仅 `local_path`）、实例 ID 和实际数据目录 |
| 现有 `workbench_list_workflows` | 列出真实工作流及定义摘要 |
| 扩展 `workbench_get_workflow` | 返回当前工作流定义、`definition_sha256` 及统一材料要求（无版本号） |
| `workbench_stage_package` | 通过 `local_path` 读取并校验源目录，预留任务 ID 并写入该任务 `.staging` |
| `workbench_finalize_package` | 完整校验、冻结修订；支持仅校验；提交后待用户启动确认 |
| `workbench_get_package` | 查询清单、资源和回执，支持幂等键查询与分页读取 |
| `workbench_get_node_context` | 返回本次节点获准使用的材料和上游产物引用 |
| 现有 `workbench_delete_task` | 调用统一清理服务，不实现独立的删除逻辑 |

暂存与正式资源都归属任务。草稿按保留期清理；取消整个创建草稿后释放预留任务和暂存目录。上传和删除对同一任务互斥，禁止边删除边创建新文件。

校验仅按统一规则：协议版本、工作流定义摘要（`definition_sha256`）、节点覆盖、资源归属、合法路径、文件完整性、输入输出引用及声明的 Schema。不因节点名为“测试”而强制出现某专属文件。

先校验并持久保存文件，再用短事务绑定正式修订，避免缺文件的任务可启动。同键同摘要返回同回执，同键不同内容拒绝；超时后先查结果，避免重复创建。

回执包含任务 ID、修订、包摘要、工作流、状态、完整性结果及真实详情地址。错误定位到具体节点或文件，未完整接收不标成功。

## 9. 节点隔离与交接

只分发当前节点文档、指令、资源和显式声明的共同资源。其他节点输出经 `input_bindings` 分发，不暴露其他节点私有资源，也不把全包拼进提示词。

`context.json` 记录任务、修订、包摘要、工作流、节点、执行 ID、尝试序号、工作目录、绑定的上游执行与产物摘要、反馈和输出位置。凭据由服务派发，不由上传者预填。

静态材料只读，当前尝试写自己的输出、日志和临时目录。通过受控路径或只读副本分发，资源接口检查归属。目录与接口隔离不等于操作系统权限隔离，不额外承诺。

输入绑定明确修订、来源执行和摘要，不依赖模糊的 `latest.md`。业务需要代码快照、数据版本时，通过通用输入标识和输出契约声明；协议不强制所有任务具有 Git 或代码快照。服务只验证显式声明的版本约束。

统一 `result.json` 包含任务、修订、节点、执行 ID、包摘要、`outcome`、摘要、问题和普通产物引用。`outcome` 为 `passed`、`failed`、`blocked`。用例结果等作为普通输出及可选 Schema 表达，不成为固定顶层测试字段。

通用基础校验通过后按冻结连线处理，运行故障暂停。节点不能指定下一节点或伪造用户操作。沿用同一后台调度，不新增第二个推进器。

## 10. 删除任务时回收全部所属资源

磁盘残留与运行时内存泄漏分别处理。任务是最终资源所有者，节点与修订只是内部归类。

删除包括：全部修订的节点文档、指令、资源、共同材料；全部尝试的输入副本、输出、执行日志和临时文件；上传草稿；数据库关联记录；进程引用、流、句柄、计时器、订阅、输出缓冲和缓存引用。

不删除业务项目、上传源文件、用户自行导出的副本、全局工作流模板或其他任务。服务日志单独管理，只保留必要操作摘要，不复制节点正文，并采用有上限的保留策略。

统一清理步骤：

1. 标记 `deleting` 并持久记录进度，拒绝新派发、上传和资源写入。
2. 停止执行并确认进程结束，关闭流、句柄和订阅，释放运行时引用。无法确认结束时保留待清理状态，禁止进程继续写入。
3. 核验任务根目录确实位于当前实例 `DATA_DIR/tasks` 内，再删除整个任务目录；不沿源路径或链接删除外部文件。
4. 文件删除成功后，事务删除任务与关联数据库记录，最后移除清理恢复记录。
5. 全部完成才返回成功；重复删除返回已删除或原清理状态。

文件占用、权限不足、数据库失败或中断时保留 `deleting/cleanup_failed` 和原因。启动恢复或用户重试继续同一清理流程，不能先永久移除任务入口再吞掉文件错误。恢复记录不复制材料，完成后也回收。

正常执行结束同样释放计时器、句柄和缓冲，不能等删任务才释放。大资源采用流或有界分页，缓存须限量并按任务可失效。清理过期草稿前检查无活动上传和执行。

删除 SQLite 记录不一定立即缩小数据库文件，不等于任务仍可访问；数据库物理压缩单独维护，不在每次删除时昂贵地压缩整库。

## 11. 修订、废弃清理与实施边界

材料修改生成新修订，使用 `expected_revision` 避免并发覆盖；每次执行独立尝试目录。运行中先停止并确认进程退出，再提交新材料并重新确认启动。历史版本保留供查阅，删除任务时一起清理。

依据 `GEMINI.md`“开发阶段不考虑兼容，废弃项直接删除”规范：本次全面切换至 `cb.task-package/2.0` 与统一节点模型，直接移除旧版全局正文字段（`task_md`、`development_md`、`tests_md`、`acceptance_md`、`verifier_prompt_md`、`worker_prompts`）及旧版 `workbench_submit_task`、`workbench_revise_task` 接口与兼容桥接代码；测试与验收不再使用硬编码全局正文或 Markdown 命令抓取，而是由通用工作流节点配置（`execution_mode`、`result_rule`）及节点独立 `node.md`、`prompt.md`、`resources/` 驱动。
