# MCP 任务包传输与节点材料规范方案

日期：2026-11-10。状态：设计草案，未实施。

本文定义 CBWorkBench 的应用层任务包协议，拟采用 `cb.task-package/2.0`。它通过 MCP 工具传输，不是 MCP 标准本身已有的任务包格式。本文所有新增字段与工具均为拟议契约。

## 1. 目标与现状

目标是让主 Agent 先通过 MCP 了解真实工作流，再按节点准备独立、完整、可校验的材料。MCP 请求优先传递结构化清单和文件引用，大段 Markdown 放在文件中。

已核对当前工作区源码：

- `src/server/mcpServer.ts` 已定义 `workbench_list_workflows`、`workbench_get_workflow`，提交接口已有 `workflow_id`、`workflow_version`、`node_prompts`。
- 提交和存储仍围绕全局 `task_md`、`development_md`、`tests_md`、`acceptance_md`、`verifier_prompt_md` 与 `worker_prompts`，没有统一的节点材料清单。
- `src/services/workflowEngine.ts` 的命令节点使用节点命令或全局测试材料；Agent 提示词仍有回退到验收提示词、Worker 提示词的路径。
- `src/storage/fileStore.ts` 仍采用固定文件布局。

以上是当前本地源码事实，不代表已经核对运行中服务或已发布版本。本次不修改实现，不上传任务，不启动工作流。

## 2. 核心约定

1. **工作流决定步骤，任务包填充具体内容。** 节点 ID、执行方式、执行器、模型、连线、结果规则和重试限制来自指定版本的工作流。任务包不能暗中改图或改变执行方式。
2. **按稳定节点 ID 绑定。** 禁止根据名称、顺序或包含“test”等字符串猜职责。
3. **每个任务节点有自己的说明与指令。** 开发、测试、验收、人工处理都独立存放材料。开始和结束是控制节点，只在清单声明，不生成无意义的模型提示词。
4. **文件路径是资源定位方式。** 工作台必须真正读取并保存文件，不能仅保存上传者机器上的路径就宣称上传成功。
5. **任务材料与运行产物分开。** 已确认材料不可原地改写；每次节点执行产生独立结果和证据。
6. **提示词无会话依赖。** 每个节点从新会话开始，输入来自明确的文件和本次运行上下文。

不固定 Worker 品牌和模型，不将当前默认开发流程硬编码进协议。节点次数限制、超时等继续采用工作流与工作台实际配置，本方案不另行重定默认值。

## 3. 先获取工作流契约

主 Agent 的准备顺序：

```text
查询任务包协议能力
  → 列出并选择工作流
  → 获取指定版本及各节点材料要求
  → 阅读真实项目代码，整理共同需求基线
  → 为每个任务节点生成独立材料与指令
  → 生成 manifest，计算文件大小与哈希
  → 本地自检并交付用户审阅
  → 获准上传后暂存、校验、正式提交
  → 等待用户在工作台启动
```

建议新增 `workbench_get_package_protocol`，返回协议版本、机器可读 Schema、字段说明、材料模板、支持的传输模式及大小限制。Schema 通过版本化资源引用按需读取，不要求一次返回所有模板全文。

扩展现有 `workbench_get_workflow`：保留真实节点字段，补充工作流摘要哈希，以及任务节点的 `material_contract`。示意：

```json
{
  "id": "test",
  "name": "独立测试",
  "type": "task",
  "execution_mode": "command",
  "material_contract": {
    "purpose": "验证本次需求与受影响的回归行为",
    "required_documents": ["spec", "test_cases"],
    "instruction_usage": "runbook",
    "required_structured_files": ["test_plan"],
    "input_slots": ["code_snapshot", "development_result"],
    "output_slots": ["result", "test_report"],
    "contract_version": "1.0"
  }
}
```

`purpose` 与材料要求由模板维护者明确配置，不能仅靠 Agent 猜测；未配置用途的自定义节点应标明信息不足。协议规定文件格式和完整性，业务用例由主 Agent 根据真实需求编写。

工作流较大时允许先查摘要，再按节点分页读取。全文读取接口须返回截断标志与后续游标，不得静默截断。

## 4. 标准目录

```text
<package-root>/
  manifest.json
  shared/
    requirements.md
    acceptance-baseline.md
  nodes/
    development/
      spec.md
      prompt.md
      development-items.md
    test/
      spec.md
      prompt.md
      test-cases.md
      test-plan.json
    acceptance/
      spec.md
      prompt.md
      checklist.md
    human_review/
      spec.md
      prompt.md
      checklist.md
```

目录名使用工作流稳定节点 ID 的安全路径编码；服务返回该映射，禁止直接将未经校验的 ID 拼接为文件路径。新增审查、文档等节点时继续使用相同结构，不新增全局固定正文参数。

| 文件 | 作用 |
| --- | --- |
| `shared/requirements.md` | 精炼背景、需求 ID、范围、项目入口、兼容约束与已知阻塞项 |
| `shared/acceptance-baseline.md` | 冻结的共同判定标准，避免不同节点各自解释需求 |
| `nodes/<id>/spec.md` | 当前节点负责什么、输入、边界、步骤、完成条件和交付物 |
| `nodes/<id>/prompt.md` | 当前节点的具体操作指令；不得只写“见上文” |
| 节点附属文件 | 开发清单、测试用例、验收清单、参考材料等，按真实契约提供 |

统一保存 `prompt.md` 是文件约定，不代表所有节点都会调用模型：

| 执行方式 | `prompt.md` 的含义 | 实际执行依据 |
| --- | --- | --- |
| `agent` | 独立 Agent 提示词 | 冻结的提示词与运行时输入 |
| `command` | 执行说明、环境及故障处理手册 | 显式声明的命令或结构化执行计划 |
| `manual` | 给人的审核、操作与退回指引 | 用户实际提交的处理结果 |

命令节点不得从自然语言提示词中猜命令。人工指令不得转成 Agent 自动批准。

## 5. Manifest：唯一的结构化入口

统一使用 `snake_case`。下例仅展示结构，`${...}` 是说明用占位符，实际提交必须替换为真实值。

```json
{
  "protocol_version": "cb.task-package/2.0",
  "task_key": "supplier-filter",
  "revision": 1,
  "title": "供应商筛选调整",
  "readiness": "ready",
  "blockers": [],
  "workspace": {
    "target_cwd": "D:/CODE/PROJECT",
    "git_head": "${actual_commit}",
    "dirty_summary": "${actual_workspace_summary}"
  },
  "workflow": {
    "id": "default",
    "version": 1,
    "definition_sha256": "${workflow_hash_returned_by_server}"
  },
  "shared_refs": [
    "shared/requirements.md",
    "shared/acceptance-baseline.md"
  ],
  "nodes": {
    "development": {
      "spec_ref": "nodes/development/spec.md",
      "instruction_ref": "nodes/development/prompt.md",
      "document_refs": ["nodes/development/development-items.md"],
      "shared_refs": ["shared/requirements.md", "shared/acceptance-baseline.md"],
      "input_bindings": [],
      "outputs": {"result": {"required": true}}
    },
    "test": {
      "spec_ref": "nodes/test/spec.md",
      "instruction_ref": "nodes/test/prompt.md",
      "document_refs": ["nodes/test/test-cases.md"],
      "shared_refs": ["shared/requirements.md", "shared/acceptance-baseline.md"],
      "execution": {
        "source": "package_plan",
        "plan_ref": "nodes/test/test-plan.json"
      },
      "input_bindings": [
        {
          "slot": "development_result",
          "from_node_id": "development",
          "output": "result",
          "required": true,
          "freshness": "current_code_snapshot"
        }
      ],
      "outputs": {
        "result": {"required": true},
        "test_report": {"required": true}
      }
    },
    "acceptance": {
      "spec_ref": "nodes/acceptance/spec.md",
      "instruction_ref": "nodes/acceptance/prompt.md",
      "document_refs": ["nodes/acceptance/checklist.md"],
      "shared_refs": ["shared/requirements.md", "shared/acceptance-baseline.md"],
      "input_bindings": [
        {
          "slot": "test_report",
          "from_node_id": "test",
          "output": "test_report",
          "required": true,
          "freshness": "current_code_snapshot"
        }
      ],
      "outputs": {"result": {"required": true}}
    },
    "human_review": {
      "spec_ref": "nodes/human_review/spec.md",
      "instruction_ref": "nodes/human_review/prompt.md",
      "document_refs": ["nodes/human_review/checklist.md"],
      "shared_refs": ["shared/requirements.md", "shared/acceptance-baseline.md"],
      "input_bindings": [
        {
          "slot": "acceptance_result",
          "from_node_id": "acceptance",
          "output": "result",
          "required": true,
          "freshness": "current_code_snapshot"
        }
      ],
      "outputs": {"result": {"required": true}}
    }
  },
  "files": [
    {
      "path": "nodes/test/test-cases.md",
      "owner": "test",
      "kind": "test_cases",
      "media_type": "text/markdown",
      "size_bytes": 1234,
      "sha256": "${actual_file_sha256}"
    }
  ]
}
```

约束：

- `nodes` 必须完整且准确覆盖工作流所有 `task` 节点，不能缺节点、多节点或替代开始／结束节点。
- 示例 `files` 只列一项；真实清单必须逐一登记所有被引用文件，包括共同材料、指令和结构化计划。未登记文件不接收，也不派发。
- 每个文件只有一个所有者：某节点 ID 或 `shared`。节点不能引用其他节点的私有文件。
- `size_bytes` 和 SHA-256 针对文件原始字节；文本使用 UTF-8 无 BOM。传输和存储不自动转换换行符。
- Manifest 不登记自己的哈希，避免自引用；提交请求单独携带 `manifest_sha256`。
- `input_bindings` 声明运行时产物依赖，不是额外控制连线。其来源必须是有效节点及已声明输出；校验成功路径和首次执行上的可满足性，不把合法返工回环当成非法依赖环。
- `readiness=ready` 只表示材料准备完整，不代表允许启动；`blocked` 草案可以保存，但不能进入待启动就绪状态。
- Schema 拒绝未知关键字段；扩展字段只能放在声明过的 `extensions` 命名空间，不静默忽略拼错的字段。

## 6. 路径引用和大文件传输

区分三种地址，禁止混用：

| 地址 | 示例 | 生命周期与用途 |
| --- | --- | --- |
| 上传源路径 | `D:/.../.cb-flow/task/r01/manifest.json` | 上传阶段，工作台读取本机文件的来源 |
| 包内相对路径 | `nodes/test/test-cases.md` | 材料之间的稳定引用，与保存位置无关 |
| 工作台资源引用 | 服务返回的不透明 `resource_ref` | 跨进程读取已接收材料或运行证据，不要求客户端共享磁盘 |

### 6.1 同机路径导入：第一版推荐的主要方式

```json
{
  "protocol_version": "cb.task-package/2.0",
  "idempotency_key": "supplier-filter:r1:${manifest_sha256}",
  "operation": "create",
  "source": {
    "mode": "local_path",
    "package_root": "D:/CODE/PROJECT/.cb-flow/supplier-filter/r01",
    "manifest_path": "manifest.json",
    "manifest_sha256": "${actual_manifest_sha256}"
  }
}
```

工作台核对允许的本地根目录，读取 Manifest 及其列举的文件，校验并复制到暂存区。即使主 Agent 以后删除原始目录，正式提交的包仍然完整可用。

源路径不可读时返回 `SOURCE_UNAVAILABLE`，不能继续保存空正文，也不能假装上传成功。客户端机器与服务端机器不同时，必须改用文件内容传输。

路径规则：包内路径统一 `/`，禁止绝对路径、盘符、`..`、网络路径和大小写归一化后的重名。实际解析后的路径必须仍在包根内；拒绝通过符号链接、Windows junction/reparse point 等逃逸。只读清单内普通文件，不递归打包整个工程、不读取隐藏凭据目录。服务读取到的实际字节必须匹配已声明哈希，源文件中途变化则失败。

### 6.2 文件内容传输：非共享磁盘时的后备方式

`source.mode=upload` 时上传 Manifest 内容，再按文件逐个传输。请求过大时按字节分块，使用 Base64，避免拆断 UTF-8 字符；服务按偏移重组并校验完整大小及哈希。

每个分块携带 `draft_id`、`path`、`offset_bytes`、`content_base64`、`chunk_sha256`。同位置同内容重试返回原结果，不同内容报冲突；未完整接收不得提交。

允许较小清单内嵌提交，禁止强迫所有 Markdown 内嵌。分块和请求大小采用服务公布的限制，不写死为某个模型的 Token 上限；Base64 膨胀及 JSON 开销计入请求限制。

路径解决上传请求大小问题，不能消除模型上下文上限。运行时仍须提供文件索引、简短摘要和分段读取能力。大材料应按用例组等语义拆分；必需材料超出读取能力时返回受阻，不能静默省略必需标准。

## 7. 统一 MCP 接口建议

以下为拟议工具，不代表当前环境已接入。

| 工具 | 主要用途 | 关键输入／输出 |
| --- | --- | --- |
| `workbench_get_package_protocol` | 获取格式、Schema、模板与能力 | 返回版本、资源引用及请求／文件／包大小限制 |
| 现有 `workbench_list_workflows` | 选择工作流 | 返回真实 ID、版本、摘要 |
| 扩展 `workbench_get_workflow` | 获取冻结依据和节点材料要求 | 指定 ID、版本；返回定义哈希、节点与材料契约 |
| `workbench_stage_package` | 暂存新包或修订包 | `operation`、幂等键、`source`；返回 `draft_id`、待上传文件、校验问题 |
| `workbench_upload_package_resource` | 上传文件内容或分块 | 草稿、包内路径、偏移、内容和哈希；返回接收进度 |
| `workbench_finalize_package` | 完整校验并正式提交 | 草稿、Manifest 哈希、幂等键；支持 `validate_only`；返回正式回执 |
| `workbench_get_package` | 读取草稿或正式包，确认不确定结果 | 按幂等键或任务与修订查询；正文按资源、分页读取 |
| `workbench_get_node_context` | 获取当前节点的运行输入 | 绑定任务、节点、执行 ID 及服务分配的执行凭据；仅返回该次有权使用的材料和产物引用 |

暂存状态为 `staging`，禁止启动。`finalize(validate_only=true)` 返回完整问题清单，无副作用；正常 finalize 完成校验后才创建正式任务的 `pending_confirm` 状态。

至少返回：`task_id`、`revision`、`status`、`workflow_id`、`workflow_version`、`manifest_sha256`、`package_digest`、完整性结果，以及服务实际提供的详情地址。第一版以 Manifest 原始字节的 SHA-256 作为 `package_digest`，但只有清单列出的全部文件均完成大小及哈希校验后才能返回完整性通过；Manifest 已登记全部文件摘要，无需再引入另一套摘要算法。上传源目录不写入 Manifest，因此移动源目录不会改变包摘要。

统一响应体：

```json
{
  "ok": false,
  "request_id": "${request_id}",
  "error": {
    "code": "MISSING_REQUIRED_MATERIAL",
    "message": "独立测试节点缺少测试计划",
    "retryable": false,
    "details": [
      {"node_id": "test", "field": "execution.plan_ref", "path": "nodes/test/test-plan.json"}
    ]
  }
}
```

工具返回的错误标记与 `ok` 保持一致。禁止只返回无法定位的“上传失败”。至少区分版本不支持、工作流哈希不符、材料缺失、路径越界、大小超限、哈希不符、修订冲突和执行输入过期。

提交的逻辑原子性：先把文件校验、保存为不可变内容，再在短事务中创建正式修订并绑定工作流；正式记录引用的文件必须已持久保存。中途失败最多留下不可启动的暂存文件，不能留下看似完整的正式任务。相同幂等键和相同摘要返回相同回执；同键不同摘要拒绝。超时后先查询该键的结果，不盲目重复建任务。

## 8. 节点隔离与运行时交接

节点执行时提供独立材料视图：

```text
<node-run-root>/
  material/       当前节点的冻结材料，只读
  shared/         仅该节点声明引用的共同基线，只读
  inputs/         本次获准读取的上游产物，只读
  runtime.json   服务生成的执行上下文
  outputs/       当前节点本次执行的产物目录
```

不将整个任务包根目录自动注入每个 Agent，也不把所有节点文档拼进所有提示词。读取资源接口按节点和执行凭据校验，禁止凭路径访问其他节点材料。共同需求通过 `shared_refs` 显式提供，不复制到各节点后各自修改。

这里首先保证目录组织、材料分发和资源接口的隔离。当前本机 CLI 如果仍有整块磁盘权限，目录和提示词本身不能提供操作系统层面的访问隔离；实现时不得将这一层设计宣传成已具备的权限沙箱。工作台管理的冻结副本和摘要不能由节点输出覆盖。

`runtime.json` 至少记录任务、修订、包摘要、冻结工作流、节点、执行 ID、尝试序号、真实工作目录、代码快照、已解析输入引用、尚未关闭的问题及完成上报协议。执行凭据由服务分配，通过受控运行通道提供，不写入静态任务包。

主 Agent 生成的是静态提示词，工作台派发时附加本次真实上下文。提示词不能预填未来的执行 ID、结果、凭据或“测试已通过”。

上游输入由服务解析并绑定到明确的 `attempt_id` 与文件哈希，不能让 Agent 自行寻找一个名为 `latest.md` 的文件：

- 测试读取当前代码状态及对应开发交付。
- 验收读取同一代码快照的测试报告、代码差异及相关开发结果。
- 返工时服务把当前未关闭问题与实际失败报告加入开发的 `inputs`；首轮明确为空，不能要求读取尚未生成的验收结果。
- 服务记录完整代码快照，覆盖未提交修改和新增文件，不能仅以 Git HEAD 表示代码状态。进入开发返工后旧测试结论不再满足当前输入条件。
- `freshness=current_code_snapshot` 既要求产物的代码摘要匹配，也要求来源执行属于当前有效的流程阶段；不能跳过本轮失败结果而回捞更早的成功结果。
- 输入缺失、过期或来源错误返回受阻，不伪装成节点业务失败，也不自动使用其他节点的同名文件。

运行产物按 `task/revision/node_id/attempt_id` 隔离。模型不能通过修改自己的指令文件改变本次判定标准。

## 9. 节点文档和指令内容规范

所有任务节点 `spec.md` 使用相同章节：

```text
节点目标与负责需求 ID
输入材料及用途
工作范围和必须保持的行为
具体工作项与操作步骤
完成条件与证据
交付物和输出格式
阻塞情况及处理方式
```

所有 `prompt.md` 必须包含：独立角色与简短背景、材料读取顺序、允许行为、禁止越权、验证要求、输出路径和失败处理。引用文件时使用当前运行视图中的相对路径，不引用主 Agent 聊天中的“上文”。

共同基线是业务标准，节点说明是当前职责，节点指令是执行要求；三者发生实质冲突时返回受阻，不能以“提示词优先”来降低验收标准。执行方式、连线及权限始终由工作台实际配置决定。

按职责增加材料：

| 职责 | 额外材料 | 核心要求 |
| --- | --- | --- |
| 开发 | `development-items.md` | 需求、真实代码入口、开发项及完成条件可追踪 |
| 测试 | `test-cases.md`、`test-plan.json` | 用例步骤与预期完整；执行入口结构化；不能把跳过算通过 |
| 验收 | `checklist.md` | 标准 ID、必需证据、阻断性及人工待办；不修改业务代码或标准 |
| 人工处理 | `checklist.md` | 人应查看什么、通过／退回条件、退回原因；保留真实用户决定 |

测试用例至少包含 ID、需求 ID、前置条件、输入、步骤、预期结果、自动／人工类别、是否必需、证据要求。已有入口与待实现入口必须区分；阻断性的自动化入口未完成时不能标为可启动。

## 10. 测试节点：文档与执行契约分开

测试说明可以很长，但执行契约必须可机器校验。`test-plan.json` 示例：

```json
{
  "schema_version": "cb.test-plan/1.0",
  "checks": [
    {
      "id": "CHECK-REGRESSION",
      "case_ids": ["TC-001", "TC-002"],
      "requirement_ids": ["REQ-001"],
      "required": true,
      "runner": "shell",
      "command": "npm test",
      "cwd": ".",
      "expected_exit_code": 0,
      "evidence": {"stdout": true, "stderr": true, "exit_code": true}
    }
  ],
  "manual_case_ids": ["TC-MANUAL-001"]
}
```

该命令是格式示例；真实包必须填入项目已核实的入口。命令本身是可执行内容，属于用户审阅的冻结材料，不能通过任意环境变量或运行时补文悄悄替换。

执行来源必须唯一：工作流节点明确采用 `workflow_command`，或在模板中允许采用任务包的 `package_plan`。两者同时提供时拒绝，禁止偷偷覆盖模板命令。模板不允许任务包提供命令时返回契约不匹配。

必需测试标准要求至少存在有效检查、真实执行完成、退出状态和证据齐全；若项目支持测试统计，应检查实际发现／执行的用例数量和必需用例覆盖。仅退出码为 0 不保证必需用例真正执行。空计划、全部跳过或缺报告不得判定通过。

人工用例只作为人工待办，不能由命令节点生成“人工已通过”。无自动化验证能力且标准要求自动验证时应受阻；不能临时把必需自动验证改成人工。

## 11. 统一节点结果

不再让不同执行器各报一种“完成”。所有节点的规范化 `result.json` 至少包含：

```json
{
  "schema_version": "cb.node-result/1.0",
  "task_id": "${task_id}",
  "revision": 1,
  "node_id": "test",
  "attempt_id": "${attempt_id}",
  "package_digest": "${package_digest}",
  "code_snapshot_id": "${code_snapshot_id}",
  "outcome": "passed",
  "summary": "本次必需自动检查已执行并满足标准",
  "checks": [
    {
      "id": "CHECK-REGRESSION",
      "status": "passed",
      "evidence_refs": ["${server_registered_report_ref}"]
    }
  ],
  "issues": [],
  "output_refs": {"test_report": "${server_registered_report_ref}"},
  "manual_checks_pending": ["TC-MANUAL-001"]
}
```

`outcome` 统一为 `passed`、`failed`、`blocked`；单项检查可为 `passed`、`failed`、`skipped`、`not_run`。业务断言不通过是 `failed`；缺输入、登录故障、运行异常、协议损坏或证据不足是 `blocked`。取消由工作台运行状态另行记录，不伪装成测试失败。

Agent 可以提交候选结果；命令结果由工作台结合真实运行记录生成；人工结果由真实用户操作生成。工作台核对结果中的身份、快照和证据引用后才登记生效，不把模型的自报字段视为真实身份或证据。

成功／失败沿冻结连线推进，受阻暂停。Agent 不能指定下一节点，不能代替命令执行证据或人工审核。现有完成报告协议应复用；上传协议不额外增加第二个调度器。

## 12. 版本、修订和兼容

- 协议主版本不兼容变更显式升级；工作流版本、任务修订和节点尝试分别计数，不能混用。
- 创建时固定 `workflow.id + version + definition_sha256`。未指定版本的选择只在准备阶段解析，正式提交必须明确版本。
- 修改任务包创建新修订，携带 `task_id` 与 `expected_revision`，防止并发覆盖；旧文件与运行记录保留。
- 正在运行时禁止替换生效材料。先停止并确认进程结束，再提交新修订，经用户重新确认启动；旧证据不得自动成为新材料的通过依据。
- 新修订在校验成功前不能覆盖旧的可查看版本，也不能自动启动。
- 旧提交接口继续走明确的旧协议路径。不能将旧任务伪装成已经具有节点隔离的 v2 任务。
- v2 不再接受与节点材料重复的全局 `worker_prompts`、`verifier_prompt_md`、`node_prompts`。迁移时若无法确定旧材料属于哪个节点，要求补充映射，禁止通过名称猜测。
- Skill 和文档随后按已实施的 Schema 更新；协议契约由工作台维护，不能只修改生成任务包的提示词而不实现服务端校验。

## 13. 第一版边界与后续实施顺序

第一版聚焦本机路径导入、节点材料契约、完整性校验、不可变修订、节点材料视图与结构化测试计划。第一版至少实现能力查询、工作流材料契约、暂存／校验／提交、回读及节点上下文读取。未实施的内容上传模式在能力查询中明确 `unsupported`，不能文档写支持而服务实际拒绝或丢失。

后续再根据真实跨机需求实现分块文件上传；保持同一 Manifest，不再设计第二种任务包。暂不引入远程文件系统、任意 URL 拉取、并行分支、插件化执行语言或操作系统权限隔离改造。

建议实施顺序：先定机器 Schema 与错误码，再实现文件导入和冻结存储，然后接入节点材料分发与结果绑定，最后更新 MCP 工具、任务详情展示和生成任务包的流程。

后续验收至少覆盖：

1. 从 MCP 获取的节点契约足以让无聊天历史的 Agent 为自定义工作流生成正确材料。
2. 开发、测试、验收各有独立文档和指令，不回退使用其他节点提示词。
3. 长文档通过本机路径导入，请求中无需粘贴全文；删除源文件后正式包仍可读取。
4. 缺文件、错误哈希、目录越界、链接逃逸、大小写重名和大小超限均定位到具体资源。
5. 任意节点通过资源接口无法读取其他节点私有文档；上游结果按绑定正常交接。
6. 上传中断不产生可启动的不完整任务，幂等重试不重复创建；查询可消除提交结果不明。
7. 空测试、跳过测试、缺证据和旧快照证据均不能绕过标准。
8. 验收失败返回开发后，开发收到真实问题，新测试和新验收使用新快照。
9. 模板更新不改变已提交任务，修订不覆盖历史记录，人工操作仍来自用户。
10. 旧接口和旧任务保持原行为，新接口不暗中改动执行器、模型、连线或执行限制。
